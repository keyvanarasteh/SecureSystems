# 03 — Çalışma Ortamları (Environments)

> Yazılım geliştirme sürecinde kullanılan **farklı ortamlar**, her birinin amacı,
> `.env` dosya yapılandırması ve ortamlar arası güvenlik farkları.
>
> Yazar: Keyvan Arasteh · İstinye Üniversitesi · 2026

---

## Neden Farklı Ortamlar Var?

Bir yazılım projesi tek bir ortamda geliştirilmez. Her aşamanın farklı
gereksinimleri vardır:

- **Development** — Geliştirici kodu yazar, hızlı geri bildirim alır
- **Debug** — Hata teşhis edilir, detaylı loglar ve profiler açılır
- **Test** — Otomatik testler çalışır, kod kalitesi doğrulanır
- **Production** — Gerçek kullanıcılar gerçek veri ile çalışır

> **⚠️ Neden ayrılmalı?**
> - Hata detayları production'da gösterilirse **saldırgan sistem yapısını öğrenir**
> - Geliştirme ortamı gerçek veritabanına bağlanırsa **yanlışlıkla veri silinebilir**
> - Debug logları production'da açık kalırsa **performans düşer, veri sızar**

---

## Ortam Karşılaştırma Matrisi

| Özellik            | Development        | Debug               | Test                | Production            |
| ------------------ | ------------------ | -------------------- | ------------------- | --------------------- |
| **Amaç**           | Özellik geliştirme  | Hata teşhisi         | Kalite doğrulama     | Kullanıcıya hizmet    |
| **Veri**            | Sahte / Seed veri   | Sahte / Seed veri    | Mock / Fixture       | Gerçek kullanıcı verisi |
| **Veritabanı**      | Lokal SQLite/Postgres | Lokal + sorgu logları | In-memory / İzole   | Yönetilen RDS/Cloud   |
| **Log Seviyesi**    | `info` / `debug`   | `trace` (maksimum)   | `warn`              | `warn` / `error`      |
| **Hata Detayı**     | Tam stack trace     | Tam + memory dump    | Sadece assertion     | **Genel mesaj** ("Hata oluştu") |
| **Kaynak Haritası** | Açık               | Açık                 | Opsiyonel            | Gizli (sadece Sentry) |
| **Optimizasyon**    | Yok                | Yok                  | Kısmi                | Tam (minify, LTO)     |
| **Dış API'ler**     | Sandbox / Lokal    | Sandbox / Lokal      | Mock                 | Gerçek endpoint       |
| **TLS/HTTPS**       | Opsiyonel          | Hayır                | Hayır                | **Zorunlu**           |
| **Gizli Bilgiler**  | `.env.local`       | `.env.local`         | CI değişkenleri      | Vault / KMS           |
| **Erişim**          | Geliştirici makine  | Geliştirici makine   | CI runner            | Cloud altyapı         |
| **Süre**            | Sürekli çalışır    | Geçici oturumlar     | PR/commit başına     | 7/24 çalışır          |

## 1. Development (Geliştirme) Ortamı

Geliştiricinin **kendi bilgisayarında** kod yazdığı ortam.

### Özellikleri

- Lokal dev sunucu (`bun run dev`, `cargo watch`)
- Hot Module Replacement (HMR) ile anlık UI güncellemesi
- Source map'ler açık — okunabilir hata izleri
- Verbose loglama (`DEBUG` / `TRACE` seviyesi)
- Mock servisler veya lokal veritabanları

### Ortam Değişkenleri

```bash
# .env.development
NODE_ENV=development
RUST_LOG=debug,tower_http=trace
DATABASE_URL=sqlite:///tmp/dev.db
VITE_API_BASE=http://localhost:3000
DEBUG=*
ENABLE_DEBUG_ROUTES=true
```

### Riskler ve Çözümler

| Risk                              | Etki                        | Çözüm                                   |
| --------------------------------- | --------------------------- | ---------------------------------------- |
| `.env` içinde gerçek şifre        | Git'e sızma                 | `.env.local` + `.gitignore`              |
| Production DB URL'si kullanma     | Yanlışlıkla veri silme      | Ortam başına ayrı veritabanı             |
| CORS/CSP kapatma alışkanlığı      | Kötü alışkanlık → prod'a geçer | Ortama özel güvenlik ayarı            |

### En İyi Uygulamalar

1. `.env.example` ile gerekli değişkenleri belgelemeye
2. Docker Compose ile tutarlı lokal servisler
3. Git hook'ları ile secret commit'lenmesini engelleme
4. **Asla** staging veya production veritabanına bağlanma

## 2. Debug (Hata Ayıklama) Ortamı

Development'ın **uzmanlaşmış alt modu** — belirli bir hatayı teşhis etmek için
ekstra araçlar açılır.

### Development vs Debug Farkı

| Özellik            | Development          | Debug                      |
| ------------------ | -------------------- | -------------------------- |
| **Amaç**           | Yeni özellik yazma   | Belirli bir hata bulma     |
| **Log Seviyesi**   | `info` / `debug`     | `trace` / `verbose`        |
| **Performans**     | Normale yakın        | **Belirgin yavaşlama**     |
| **Enstrümantasyon** | Minimum             | Yoğun (profiler, tracer)   |
| **Süre**           | Sürekli              | Geçici, hedefli oturumlar  |

### Ortam Değişkenleri

```bash
# .env.debug
RUST_BACKTRACE=full
RUST_LOG=trace
NODE_OPTIONS=--inspect
VITE_DEBUG=true
SQL_LOG=true
TOKIO_CONSOLE=true
```

### Güvenlik Uyarısı

> **🔴 Debug modu iç yapıyı açığa çıkarır. ASLA production'da çalıştırmayın.**

| Risk                        | Etki                     | Çözüm                          |
| --------------------------- | ------------------------ | ------------------------------- |
| Verbose hata mesajları      | İç yollar, DB şeması ifşa | Ortama göre hata detayı filtrele |
| Açık debug portları (9229)  | Uzaktan kod çalıştırma   | Sadece `127.0.0.1`'e bağla     |
| Sorgu logları stdout'ta     | Kimlik bilgisi sızması   | Hassas parametreleri maskele    |

### Debug Araçları

```bash
# Rust — GDB ile hata ayıklama
rust-gdb target/debug/your-app

# Node.js — Chrome DevTools
NODE_OPTIONS="--inspect-brk" bun run dev

# Veritabanı sorgu logları — SeaORM
# sqlx_logging(true) + sqlx_logging_level(Trace)
```

### En İyi Uygulamalar

1. Debug oturumlarını **süre sınırlı** tutun — trace logunu sürekli açık bırakmayın
2. `console.log` yerine **conditional breakpoint** kullanın
3. Optimize etmeden önce **profil çıkarın** (`perf`, `flamegraph`, Chrome Performance)
4. Bulguları **issue tracker'a** yazın

## 3. Test Ortamı

Otomatik testlerin çalıştığı **izole, tekrarlanabilir** ortam.

### Özellikleri

- CI/CD runner'ları (GitHub Actions, GitLab CI)
- İzole veritabanları (SQLite in-memory, test-specific Postgres)
- Mock dış servisler (API stub, sahte ödeme sistemi)
- Deterministik seed veriler
- Kod kapsama (coverage) ölçümü

### Test Türleri

| Tür            | Kapsam               | Hız      | Ortam                   |
| -------------- | -------------------- | -------- | ----------------------- |
| **Unit**       | Tek fonksiyon/modül  | ~ms      | In-memory, mock deps    |
| **Integration** | Birden fazla modül + DB | ~saniye | SQLite veya test DB     |
| **E2E**        | Tam yığın (browser + API) | ~dakika | Playwright + test server |
| **Snapshot**   | UI bileşen çıktısı   | ~ms      | JSDOM / happy-dom       |

### Ortam Değişkenleri

```bash
# .env.test
NODE_ENV=test
DATABASE_URL=sqlite::memory:
API_SECRET=test-secret-key
DISABLE_RATE_LIMIT=true
MOCK_EXTERNAL_APIS=true
CI=true
RUST_LOG=warn
RUST_BACKTRACE=1
```

### Riskler ve Çözümler

| Risk                      | Etki                    | Çözüm                          |
| ------------------------- | ----------------------- | ------------------------------- |
| Gerçek API'lere istek     | Flaky test, beklenmeyen ücret | Tüm dış servisleri mockla  |
| Paylaşılan test DB        | Test kirliliği          | Test suite başına izole DB      |
| Hardcoded test verisi     | Kırılgan testler        | Factory/builder pattern kullan  |
| Coverage eşiği yok        | Aşamalı kalite düşüşü  | CI'da minimum seviye zorla      |

### Kalite Kapıları (Gates)

| Kapı              | Araç            | Eşik            |
| ----------------- | --------------- | ---------------- |
| Tip Güvenliği     | `svelte-check`  | 0 hata           |
| Lint Kuralları    | ESLint          | 0 hata, 0 uyarı  |
| Unit Testler      | Vitest          | %100 başarı      |
| Kod Kapsama       | v8/lcov         | ≥ %80 satır      |
| Rust Testleri     | `cargo test`    | %100 başarı      |
| Güvenlik Denetimi | `bun audit`     | 0 kritik         |

## 4. Production (Üretim) Ortamı

Gerçek kullanıcılara gerçek veri ile hizmet veren ortam. **Her hata para ve
güven kaybına yol açar.**

### Özellikleri

- Optimize edilmiş build'ler — minified, tree-shaken, sıkıştırılmış
- Minimum loglama — sadece `warn` / `error`
- Gerçek veritabanları — yönetilen, yedekli, replike
- Her yerde TLS — HTTPS, şifreli bağlantılar
- İzleme ve uyarı — Sentry, Prometheus, Grafana
- **Sıfır debug araçları** — dev rotaları yok, detaylı hata yok

### Ortam Değişkenleri

```bash
# .env.production — ASLA GIT'E KOMMİT EDİLMEZ
NODE_ENV=production
RUST_LOG=warn,tower_http=info
DATABASE_URL=postgres://prod:***@rds.aws/prod_db
REDIS_URL=rediss://***@elasticache/0
SENTRY_DSN=https://***@sentry.io/***
API_SECRET=(vault/KMS ile yönetilir)
CORS_ORIGINS=https://app.example.com
```

### Kullanıcıya Gösterilen Hata Farkı

```
┌─────────────────────────────────────────────────────────┐
│ DEVELOPMENT / DEBUG                                     │
│                                                         │
│ Error: Cannot read property 'id' of undefined           │
│   at UserService.getUser (src/services/user.ts:42:15)   │
│   at Router.handle (src/router.ts:128:8)                │
│   at processTicksAndRejections (node:internal:85:5)     │
│                                                         │
│ Database: postgres://dev:dev123@localhost:5432/dev_db    │
│ Request ID: abc-123-def-456                             │
└─────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────┐
│ PRODUCTION                                              │
│                                                         │
│ Bir hata oluştu.                                        │
│ Teknik ekibimize bildirildi.                            │
│                                                         │
│ Referans: #REQ-abc123                                   │
└─────────────────────────────────────────────────────────┘
```

> **Neden?** 600.000 kullanıcınız varsa:
> 1. Hata detaylarını **görmemeli** — sistemin iç yapısını öğrenip hacklemeye çalışır
> 2. Ekstra loglar **performansı düşürür** — her isteğe trace yazmak gerekmez
> 3. Gerçek DB bilgisi **asla** hata mesajında görünmemeli

### Production Güvenlik Kontrol Listesi

- [ ] Tüm ortam değişkenleri Vault/KMS'den (`.env` dosyasından değil)
- [ ] HTTPS zorunlu (HSTS header ayarlı)
- [ ] Veritabanı yedekleri doğrulanmış (test edilmiş geri yükleme)
- [ ] Rate limiting yapılandırılmış
- [ ] Hata izleme (Sentry) bağlı
- [ ] Health check endpoint (`/health`) yanıt veriyor
- [ ] Loglama `warn` seviyesinde (debug/trace yok)
- [ ] Source map'ler Sentry'ye yüklendi (herkese açık değil)
- [ ] CSP, CORS ve güvenlik header'ları yapılandırıldı
- [ ] Graceful shutdown (`SIGTERM`) yönetimi eklendi

## `.env` Dosya Yapısı ve Hiyerarşisi

`.env` dosyaları ortam değişkenlerini tutar. Her ortamın **kendi `.env` dosyası** vardır.

### Dosya Akışı

```
.env.example              ← Şablon (git'e commit edilir, değerler BOŞ)
   │
   ├── .env.development   ← Lokal geliştirme varsayılanları
   ├── .env.debug         ← Debug üzerine yazmaları (gitignore'da)
   ├── .env.test          ← CI test değerleri
   └── .env.production    ← ASLA git'te olmaz (Vault/KMS)
```

### Öncelik Sırası (Yüksekten Düşüğe)

```
1. Çalışma zamanı ortam değişkenleri (OS seviyesi)
2. .env.{ortam}.local     (gitignore'da — kişisel üzerine yazmalar)
3. .env.{ortam}           (commit edilir — hassas olmayan değerler)
4. .env.local             (gitignore'da — tüm ortamlar)
5. .env                   (commit edilir — varsayılan değerler)
```

### `.env.example` Şablonu

Bu dosya **değerleri boş** bırakarak gerekli değişkenleri belgeler:

```bash
# ─── Sunucu ───
NODE_ENV=
PORT=
API_SECRET=

# ─── Veritabanı ───
DATABASE_URL=
REDIS_URL=

# ─── Dış Servisler ───
SENTRY_DSN=
SMTP_HOST=
SMTP_PORT=

# ─── Güvenlik ───
CORS_ORIGINS=
ENABLE_DEBUG_ROUTES=
```

### `.gitignore` ile Koruma

```gitignore
# Ortam değişkenleri — hassas veriler
.env
.env.local
.env.*.local
.env.production
.env.debug

# Şablon commit edilir
!.env.example
```

## Ortam Tespiti (Kodda)

### TypeScript / Svelte (Vite)

```typescript
const isProd = import.meta.env.PROD;        // boolean
const isDev  = import.meta.env.DEV;         // boolean
const mode   = import.meta.env.MODE;        // 'development' | 'production' | 'test'
```

### Rust

```rust
fn is_production() -> bool {
    std::env::var("ENVIRONMENT")
        .unwrap_or_default()
        .eq_ignore_ascii_case("production")
}

fn is_debug() -> bool {
    cfg!(debug_assertions)  // Compile-time kontrol
}
```

### Koşullu Kod

```rust
// Derleme zamanında — debug kodunu production binary'ye dahil etme
#[cfg(debug_assertions)]
pub mod debug_routes;

// Çalışma zamanında — flag ile kontrol
if std::env::var("ENABLE_DEBUG_ROUTES").is_ok() {
    router = router.merge(debug_routes());
}
```

```svelte
<!-- Svelte — sadece geliştirme modunda göster -->
{#if import.meta.env.DEV}
  <pre class="debug-overlay">{JSON.stringify(debugData, null, 2)}</pre>
{/if}
```

## Terfi Boru Hattı (Promotion Pipeline)

Kod, ortamlar arasında şu sırayla ilerler:

```
Geliştirici Makinesi         CI/CD                     Cloud
┌──────────────────┐   ┌──────────────────┐   ┌──────────────────┐
│   Development    │──→│      Test        │──→│   Production     │
│                  │   │                  │   │                  │
│ • Kod yazma      │   │ • Lint           │   │ • Deploy         │
│ • Lokal test     │   │ • Tip kontrolü   │   │ • İzleme         │
│ • Debug          │   │ • Unit testler   │   │ • Uyarı          │
│                  │   │ • Entegrasyon    │   │                  │
└──────────────────┘   │ • E2E            │   └──────────────────┘
                       │ • Güvenlik       │
                       └──────────────────┘
```

## Sık Yapılan Hatalar (Anti-Pattern)

| Anti-Pattern                      | Risk                      | Çözüm                             |
| --------------------------------- | ------------------------- | ---------------------------------- |
| "Benim makinemde çalışıyor"       | Ortama özel hatalar       | Docker + CI eşitliği              |
| Tüm ortamlar aynı DB              | Veri bozulması            | Ortam başına izole DB             |
| Prod secret'ları dev'e kopyalama  | Kimlik bilgisi ifşası     | Ayrı secret store'lar            |
| Test ortamını atlama              | Hata production'a ulaşır  | Zorunlu CI kapıları              |
| Prod'da debug flag'leri           | Bilgi ifşası              | Build-time ortam kapılama         |
